# Synthesis: Cracking complex register-allocation walls in CW 1.3

## (1) Brute annealing is NOT viable — allocator guidance is required

**Settled empirically, not by argument.** Two max-budget permuter runs on confirmed pure-reg-alloc walls made **literally zero progress**:

- `fn_800E3604` (gs_material): **2309 iterations**, best score frozen at base **75** (15 register-name diffs, 0 reorder/0 ins/0 del — 87/87 instructions identical in order and mnemonic, a clean 3-cycle `r29→r31→r30→r29`). Improved **0 times**.
- `fn_800E5790`: **1930 iterations**, best score frozen at base **150**. Improved **0 times**.

The reason is structural, not budget: the score landscape has a **discontinuous cliff right above base** (75→80→510; 150→290). There is no downhill gradient because (a) the permuter's `PENALTY_REGALLOC=5` is a *flat per-field* penalty that is blind to consistent register *renaming* — a pure bijection scores as N independent penalties — and (b) every directed C transform tried (`variants_3604.sh`: decl-reorder, slot-match-last, pointer-walk) moved the coloring **monotonically further away** (125, 320, 585). A correct *intermediate* coloring scores worse before it scores 0, so SA actively walks away from it. This is also why no GCN decomp project (tww, melee, prime) has cracked these — they all use the same random/SA permuter against the same wall.

**Verdict:** more compute cannot reach these colorings. The fix must operate on the allocator's actual decision variable (liveness/first-definition), not on edit-distance.

## (2) What we learned that lets us CONTROL the coloring

CW 1.3's GPR allocator is **deterministic and largely invertible** (confirmed in `ALLOCATOR_MODEL.md` from 13 controlled one-factor experiments + real-file corroboration):

- **The single load-bearing knob is FIRST-DEFINITION ORDER of call-surviving values** — not declaration order, not use order. Proven invariant: reversing declarations (`e_declrev5`) or uses (`e_rev5`) yields *identical* register maps; scrambling first-def order (`e_usefirst`) tracks the change exactly.
- Among values that survive ≥1 call, saved GPRs `r(32−k)..r31` fill **ascending by first-definition order**. Params count as defined-at-entry, left-to-right.
- **Short-lived values** (produced and consumed before the next `bl`) never get a saved reg — they stay volatile in r3. Only call-survivors compete for r14–r31.
- **Dead-value register recycling** is real (linear-scan slot reuse), confirmed on the real `stmw_sparse.c`.
- **Band bottom = r(32 − survivor_count)**; **stmw/lmw threshold = exactly 5** saved regs. So matching the *survivor count* matters as much as the order (it sets the prologue form).
- Clean ascending rule holds for n=5–8 survivors (covers nearly all real wall functions); a first-value-lifts-to-r31 anomaly appears only at n≈12+.

**The inversion recipe:** read the target asm, list saved-reg consumers (`mr rK,r3` / first writer of each rK) in **ascending reg order**; that is the exact sequence your C must **first-assign** the corresponding values. Keep declaration and use order free for readability. Ensure target-volatile values are produced-and-consumed without straddling a `bl`, target-saved values *do* straddle one, and the survivor count matches.

**The honest caveat (the wall inside the wall):** decl/first-def order drives BOTH register assignment AND instruction scheduling, and they're coupled. On `fn_800E3604` the coloring is *already solved* by reorder — the 4-op residual is pure **instruction scheduling** (same regs, reordered prologue ops), which is **not C-controllable** in the general case. So the method splits cleanly: **register ASSIGNMENT = steerable; instruction SCHEDULING = detect-and-triage-out, don't grind.**

## (3) The single most promising METHOD + this week's first experiment

**Method: the coloring-aware oracle + constraint-directed first-definition search** (a directed, allocator-modeled loop replacing blind annealing). It is the highest-ROI piece because it (a) makes the search see "you are 1 swap away" instead of "8 mismatches," (b) automatically separates the winnable assignment layer from the unwinnable scheduling layer, and (c) reuses tooling that already exists (`mwcceppc`, objdiff JSON, the `ra/` harness, 16 cores).

**Concrete first experiment this week (prototype against `fn_800E3604`, the controlled case):**

1. **Build the coloring-aware oracle** (`extract_coloring` over objdiff JSON — registers are already parseable as `parts[].arg.opaque='rN'`). Align target vs yours by mnemonic+operand-shape; collect the implied `yours_reg→target_reg` map per operand.
   - If a **single bijection on r14–r31** explains all reg diffs → report **"PURE RENAME, distance = minimal cycle-decomposition length"** and emit the target coloring as constraints.
   - If no single bijection but operands match after removing branch/sched diffs → report **"SCHEDULING-ONLY residual → TRIAGE OUT"** (never anneal).
   - **Acceptance check:** on `fn_800E3604` it must immediately report "coloring solved, scheduling-only residual, 4 ops." That validates the oracle against ground truth in one shot.

2. **Wire constraint-directed first-definition search.** From the oracle's `value → target physical reg` constraints, invert the `ALLOCATOR_MODEL.md` rule: solve for the first-assignment order yielding those regs (an assignment/topological problem over the live-across-call set — typically <8 survivors, so <8! and usually a *unique* consistent order, NOT N!). Materialize each candidate by reordering first-assignment statements, batch-compile across 16 cores with the exact flags, score with the oracle. Accept on byte-match; otherwise report the residual as scheduling.

3. **Validate the allocator model on held-out solved fns** (cheap, reuses the corpus): does `predict_coloring(first_def_order, survivor_count)` reproduce the *actual* compiled coloring on solved functions >80%? This both confirms the rule and quantifies where it breaks (the n≥12 anomaly).

This is a bounded directed search of ~10s–100s of candidates per function, not millions of random ones.

## (4) Honest split of the ~2000 — how many are actually addressable

From `walltriage.py` across the 6 wall-heavy files (**899 functions with ≥8 mismatches**, the hard tier):

- **Pure / dominant register-alloc (addressable by this method): ~2.6%** — 5 strict pure-reg (STRUCT==0, REG-IMM==0) + 2 reg+imm + 16 reg-dominant = **23 functions**.
- **Structural (different instructions / control-flow / scheduling): 91.4%** — **822 functions**. Even by *mismatched-instruction volume* (67,883 instrs): STRUCT **72.5%**, PURE-REG 17.0%, REG-IMM 8.4%. The cascade *mass* is structural, not coloring.
- Pure-reg walls are **concentrated in small accessor / function-pointer-table files** (gs_event_exec ~55% reg-addressable, gs_render ~20%) and **essentially absent in colosseum_battle (0/414)**, which is dominated by the `stmw`-threshold and boolean-materialize idiom walls (compiler-version-locked, not C-flippable).

**Extrapolating to the full ~2000:** expect **single-digit-percent (~3–6%, order of ~60–120 functions)** to be genuinely pure/dominant-reg-alloc-addressable. A meaningful, real, previously-unreachable chunk — but **not** the bulk of the wall. The majority (~90%) need different instructions/control-flow/scheduling and will not yield to coloring control. The method's *second* highest-value output is therefore the **triage gate itself**: classifying every near-miss as PURE-RENAME / SCHEDULING-ONLY / STRUCTURAL up front converts thousands of wasted annealing-hours into a fast skip, and tells you which functions are truly fundamental (stmw-threshold, idiom-lowering, scheduling-locked) so they're never re-attacked.
