===== PLAN =====
 Direct answers below.

## (1) Do they CRACK the hard reg-alloc/scheduling functions, or wrap them as asm?

**They wrap them. They do not crack them.** This is the honest, unanimous verdict across all four probes and it matches your own conclusion.

No mature GC/Wii project (TWW, Prime, Pikmin2, SMG/Petari) defeats genuine data-flow-locked register allocation or opposite-direction instruction scheduling by being cleverer with C. The one project that built a tool *stronger* than decomp-permuter (Sims2's asm_processor: cross-function instruction injection, forced reg assignment, scheduling mutators) explicitly **rejects its own output as not a legitimate match** and logs those functions in a `walls.md` backlog. Melee, the one strict byte-exact-only project, has sat at ~69% for years precisely because it refuses the escape valve. Everyone else retires the wall functions one of two ways:

- **"Equivalent" tier** — ship clean, logically-correct C that does *not* byte-match, still counts toward completion, excluded only from the byte-verify gate (Pikmin2/TWW `configure.py`).
- **asm-wrapper** — `INLINE_ASM`/`NON_MATCHING` ifdef keeps the ROM byte-identical; objdiff v3's `.NON_MATCHING`-label auto-strip keeps it out of the progress %.

So: **the real gap is NOT a missing cracking technique. There is no tool or method that genuinely source-cracks these.** The gap is (a) exact per-TU toolchain, and (b) a completeness model that lets you stop grinding them.

## (2) Top 3 things we are likely MISSING (ranked by impact)

**#1 — Exact per-TU compiler version + codegen-flag discrimination, driven by code ORIGIN, not a uniform GC/1.3 default.** This is the highest-impact gap and the one most likely to be manufacturing *fake* walls. The structural facts:
- `mw_comment_version: 8` in our config.yml is a **linker fingerprint**, not a compiler selector — one linker covers many mwcceppc builds. Reading it as "the compiler" is a category error.
- Mature projects pin compiler+flags **per library group** in the build script (TWW ships three simultaneously: GC/1.2.5n for Dolphin SDK, GC/1.3 for MSL/Runtime, GC/1.3.2 for game code). We run near-uniform 1.3 with a handful of overrides — we have *not finished* per-TU version assignment.
- The wrong version OR a wrong codegen-shaping flag produces *exactly* the symptom we call a wall: persistent reg-assignment + scheduling drift that permuter can't anneal (because permuter reshuffles C; it cannot change the allocator a different mwcc build/flag would use).
- **`-use_lmw_stmw on/off` IS the stmw threshold** — our documented "stmw wall" is very plausibly this flag, not an unbreakable idiom. Likewise untested: `-inline {auto,noauto,deferred,off}`, `-O4,p` vs `-O3,s`, `-schedule on/off`, `-fp_contract`, `-ipa file/program`.
- Our own `compiler_comparison_results.json` already shows files recommending 1.3 vs 1.2.5n inconsistently — direct local evidence some "walls" sit in mis-versioned TUs.

**#2 — Per-TU split + inline-control levers (the upstream-of-allocator knobs we've never tried).** TU boundaries change MWCC's whole-CU scheduling/regalloc context; our gs_title notes literally mark "split the file" as *untested*. Plus the inline levers that reshape the live-range graph feeding the allocator — `-inline deferred` (reverses TU function order; never tried), `#pragma inline_max_size(N)` / `inline_max_auto_size` / `auto_inline off` / `dont_inline`. Inlining decisions are the usual *upstream* cause of a "reg-alloc permutation" that has no in-function fix. These are documented, project-proven (Prime/TWW), and absent from our pragma catalog.

**#3 — A two-axis completeness model + Equivalent tier + walls.md ledger.** We are measuring success as byte-exact-or-nothing, which (a) artificially depresses our headline number vs peers who report "decompiled %" separately from "linked %", and (b) keeps us re-spending agent budget on functions the entire field accepts as unmatchable. We're missing: the Equivalent tier in config, the `-DSKIP_ASM=1` dual-build + `.NON_MATCHING` auto-strip plumbing, and a `walls.md` that logs each confirmed wall ONCE (with class: stmw-threshold, carry-vs-sign bool, commutative-fresh-reg add, opposite scheduling) and HARD-SKIPS it.

*(Lower-priority, real but secondary: objdiff per-unit `symbol_mappings` to recover phantom jumptable/reloc-NAME mismatches; a Mizuchi-style closed LLM loop feeding objdiff diff + mwcc stderr back into the prompt. Worth doing, but they don't crack walls either — they recover mis-scored near-matches and tighten iteration.)*

## (3) Single highest-value action

**Build and run a per-TU compiler-version × codegen-flag sweep harness, scored by objdiff-cli, BEFORE classifying any residual as a reg-alloc/scheduling wall — and validate cheaply at the asm level first with the existing `tools/decomp_work/ra/` mwcc -S harness.**

Concretely: for each stuck TU, cross `mwcc {1.2.5n, 1.3.2, 2.0, 3.0a5}` × `{-inline auto/noauto/deferred/off}` × `{-use_lmw_stmw on/off, -O4,p vs -O3,s, -schedule on/off, -fp_contract on/off}` × your existing pragma matrix. Use the three ground-truth version oracles to seed it (link-date-nearest mwcceppc build; SDK init compiler-build strings printed in the .dol; trial-fit on functions already at 100% in that file). Target `-use_lmw_stmw off` at the "stmw wall" specifically — that single flag may dissolve a whole documented wall class.

This is the highest-value action because it directly attacks the #1 gap, it is the lever mature projects actually use against these walls (not permuter), and it is cheap to falsify per-function via the local `mwcc -S` harness before any C rewrite. Permuter stays the *last* step — regalloc-only polish — never the tool to overcome a wrong toolchain.

**Bottom line:** They wrap them as asm/Equivalent too. There is no secret cracker. Our real, addressable gap is exact per-TU toolchain (version + the handful of codegen-shaping flags, especially `-use_lmw_stmw` for the stmw wall) plus a completeness model that lets us stop grinding the genuine walls — in that order.
